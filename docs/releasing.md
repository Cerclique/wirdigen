# Releasing

The changelog is generated by [git-cliff](https://git-cliff.org) from conventional commits using `cliff.toml`. Spec §12.4 is the source of truth for the flow.

## Commit groups

| Commit | Changelog group |
|---|---|
| scope `diagnostics` (any type) | **New warnings** |
| `feat!`, `fix!`, … | Breaking changes |
| `feat` / `fix` / `perf` / `docs` / `refactor` | Features / Bug fixes / Performance / Documentation / Refactoring |
| `build`, `ci`, `test`, `style`, `chore`, and the `deps` scope | omitted |

A PR that adds a warning must use the `diagnostics` scope in its title, for example `feat(diagnostics): warn on shadowed fields`. Users running `--deny-warnings` rely on that group (spec §6.5).

## Release steps

1. Branch `release/vX.Y.Z` from `main` and bump the version in `Cargo.toml` (workspace version and the internal `=` dependency pins).
2. Generate the entry: `git cliff --unreleased --tag vX.Y.Z --prepend CHANGELOG.md`. Check the diff: the new section must be dated and sit under the file header.
3. Open a PR titled `chore: release vX.Y.Z`.
4. Once merged, tag the merge commit `vX.Y.Z` and push the tag.
5. `release.yml` verifies that the tag matches the manifest version and that `CHANGELOG.md` has a dated section, publishes to crates.io, drafts the GitHub Release (`--prerelease` for `-alpha`/`-beta`/`-rc`), attaches binaries (with completions and man pages, SHA-256 checksums and build provenance) and the JSON Schema, then publishes the Release. A failed binary job leaves the Release as a draft: rerun the failed jobs, which reuse the draft and overwrite its assets.

## First v1 entry

The `1.0.0-alpha.1` section of `CHANGELOG.md` is hand-written (ADR 0003). On its release PR, replace `TBD` with the release date and skip step 2: git-cliff would otherwise generate an entry from the whole pre-release history. After `v1.0.0-alpha.1` is tagged, `git cliff --unreleased` only covers commits since that tag.

## One-time Trusted Publishing setup

`release.yml` publishes with [crates.io Trusted Publishing](https://crates.io/docs/trusted-publishing): it exchanges the workflow's OIDC identity for a short-lived token, so no API token is stored in the repository. The maintainer sets this up once:

1. **GitHub environment.** In the repository settings, create an environment named `release`. Optionally add yourself as a required reviewer, so a pushed tag waits for approval before publishing.
2. **First publish of a new crate.** Trusted Publishing can only be configured on a crate that already exists. `wirdigen` has 0.x releases, so skip this for it. `wirdigen-cli` has never been published: publish it once by hand with a scoped API token, `wirdigen` first because the CLI depends on it. Use a throwaway pre-release version that the workflow will not reuse, then revoke the token.
3. **crates.io, per crate.** Under each crate's *Settings → Trusted Publishing*, add a GitHub configuration:
   - Repository owner: `Cerclique`
   - Repository name: `wirdigen`
   - Workflow filename: `release.yml`
   - Environment: `release`

   Do this for both `wirdigen` and `wirdigen-cli`.
4. Optionally, once Trusted Publishing works, tick *Require trusted publishing* on each crate to disable token publishing.

Both crates are published in one `cargo publish --workspace` run, in dependency order. If it fails part-way, check crates.io for which crates were published before deciding how to proceed: a published version can never be re-published.
